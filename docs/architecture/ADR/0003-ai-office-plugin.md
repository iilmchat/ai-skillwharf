# ADR 0003: AI-Офис как опциональный плагин

**Статус:** Принято
**Дата:** 2026-11-12
**Контекст:** Проектирование визуализации работы агентов.

## 1. Контекст и постановка проблемы

Пользователю сложно понять, что происходит во время выполнения задачи: агент
анализирует запрос, вызывает инструменты, ждёт подтверждения или завершил
работу. Текстовый чат показывает только финальный ответ и промежуточные
фрагменты, но не даёт наглядной картины состояния агента.

Нужен визуальный слой **AI-Офис**, который показывает агентов и их статусы в
реальном времени. При этом визуализация не должна становиться обязательной
частью ядра: инсталляции без неё, headless-сценарии и интеграции с
мессенджерами должны работать как раньше.

## 2. Рассмотренные альтернативы

1. **Модуль внутри ядра Gateway.** Визуализация как обязательная часть
   бэкенда и Web UI.
   * *Минусы:* ядро начинает зависеть от деталей рендеринга, растёт связность,
     а отключить офис без правок ядра нельзя. Любое изменение визуализации
     требует релиза API.
2. **Отдельный плагин, подписанный на события Gateway.** Ядро публикует
   нейтральные события о статусах агентов, а визуальный слой интерпретирует
   их по-своему.
   * *Плюсы:* опциональность, изоляция рендеринга, независимый релизный цикл,
     возможность заменить визуализацию, не трогая агентный рантайм.
3. **Сторонний виджет/iframe.** Полностью внешний UI, встроенный в страницу.
   * *Минусы:* сложнее синхронизировать состояние и авторизацию, выше
     стоимость интеграции на старте.

## 3. Решение

**AI-Офис — это опциональный плагин визуализации, а не часть ядра.**

Ядро (Gateway) остаётся источником истины о состоянии агента и публикует
нейтральные события `office_event` по WebSocket. Плагин подписывается на них,
хранит только локальное состояние отображения и не влияет на выполнение
задач. Если плагин не установлен или отключён, ядро работает без изменений:
события просто некому обрабатывать.

Контракт события на MVP:

```json
{
  "agentId": "default",
  "status": "working",
  "task": "Анализ запроса"
}
```

Поддерживаемые статусы MVP: `working` и `waiting_approval`. Статус
`waiting_approval` отправляется, когда для продолжения задачи требуется
подтверждение пользователя; до появления полноценного approval-flow он может
выставляться вручную.

Для MVP визуализация реализуется на **React + CSS**: агенты и их карточки —
обычные DOM-элементы, анимации — CSS-переходы. Это даёт максимальную скорость
разработки и переиспользует существующий стек Web UI.

**PixiJS отклонён для MVP.** WebGL-рендеринг оправдан при большом количестве
спрайтов, сложной физике и изометрической графике, но для нескольких агентов
и статусных карточек он добавляет движок, ассеты и отдельную модель рендеринга.
К PixiJS можно вернуться, если React+CSS перестанет справляться с нагрузкой
или потребуется полноценная игровая сцена.

## 4. Последствия (Consequences)

**Положительные:**

* **Опциональность:** AI-Офис можно не устанавливать; ядро и остальные
  клиенты не зависят от визуального слоя.
* **Изоляция рендеринга:** изменения UI не затрагивают агентный рантайм,
  биллинг и песочницу.
* **Скорость MVP:** React+CSS не требуют нового движка, ассетов и
  pipeline сборки.
* **Расширяемость:** плагин может добавить собственные статусы и анимации,
  пока ядро публикует базовый контракт.

**Отрицательные / Риски:**

* **Контракт событий становится публичным.** Изменения полей `office_event`
  нужно версионировать и документировать.
* **Ограничения CSS-анимаций.** Для сложных сцен и большого числа агентов
  может потребоваться переход на canvas/WebGL.
* **Дублирование состояния.** Плагин хранит проекцию состояния для
  отображения; при переподключении сокета её нужно восстанавливать из
  очередного события или снимка состояния.
