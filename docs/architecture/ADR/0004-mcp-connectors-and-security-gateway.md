# ADR 0004: MCP-Коннекторы и Runtime-Безопасность (Agent Gateway)

**Статус:** Утверждено
**Дата:** 2026-11-13
**Контекст:** Рынок 2026 года требует управляемой автономии. 89% предприятий используют MCP. Модель больше не считается границей безопасности (defense-in-depth).

## 1. Контекст

Сейчас наши навыки (Skills) для Ozon и WB используют прямые вызовы (Mock). Это не масштабируется. Кроме того, Prompt Injection может заставить агента выполнить вредоносный код или отправить данные на сторонний сервер.

## 2. Решение

1. **MCP как стандарт:** В спецификацию `SKILL.md` добавляется поле `mcp_endpoint`. Навыки могут быть «обертками» над внешними MCP-серверами.
2. **Agent/MCP Gateway:** Создается отдельный слой (runtime-контроль), который перехватывает все вызовы инструментов (Tools) и проверяет аргументы на соответствие политикам (policy-as-code) до их исполнения в песочнице.
3. **FQDN-aware Egress:** В `SKILL.md` добавляется поле `egress_allowlist` (список доменов, к которым разрешено обращаться). Песочница блокирует любой сетевой трафик за пределами этого списка.

## 3. Последствия

* **Плюсы:** Защита от эксфильтрации данных. Возможность подключать тысячи готовых MCP-серверов.
* **Минусы:** Усложнение логики Gateway (дополнительная проверка каждого вызова).

## 4. Реализация (Sprint 14)

Пункты 1–3 решения реализованы в коде:

* **Agent Gateway** (`apps/api/src/security/`): декларативный policy engine
  вместо regex-правил. Реестр `tool-policies.ts` описывает для каждого
  инструмента strict Zod-схему аргументов, требуемое разрешение навыка,
  роли, категорию egress и режим taint. `shell-analyzer.ts` структурно
  разбирает команды и работает по allowlist бинарников (без regex по
  сериализованным аргументам), `secret-taint.ts` отслеживает секрето-подобные
  значения из недоверенных источников (блокировка в каналах эксфильтрации,
  маскировка в поиске). Блокировки пишутся в append-only `AuditLog`.
* **MCP Gateway** (`apps/api/src/llm/tools/mcp-gateway.ts`): отдельный слой
  проверки вызовов до отправки на MCP-сервер, `mcp_endpoint` из манифеста как
  источник адреса, единый JSON-формат ошибок (400/502/503/504), осознанные
  таймауты и retry только для временных транспортных сбоев.
* **FQDN-aware egress** (`apps/api/src/sandbox/`, `apps/sandbox-worker/`):
  `egress_allowlist` из манифеста → iptables-allowlist в сетевом namespace
  sandbox-контейнера; без списка сеть запрещена (deny by default), глобальные
  флаги больше не включают egress. Остаточные риски (IP-pinning, DNS-туннель,
  ip6tables) зафиксированы в KI-028, эвристичность shell-анализатора — в
  KI-029, неполные per-action схемы MCP — в KI-027.
* **Seccomp** (ADR 0005): в staging применяется кастомный default-deny профиль
  `sandbox/seccomp-profile.json` (KI-005).

Границы безопасности не изменились: Gateway и policy engine не выполняют
сторонний код — его исполняет только `sandbox-worker` в изолированном
контейнере, а policy engine является слоем defense-in-depth.
