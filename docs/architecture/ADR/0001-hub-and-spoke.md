# ADR 0001: Выбор паттерна Hub-and-Spoke для архитектуры Gateway

**Статус:** Принято
**Дата:** 2026-11-12
**Контекст:** Проектирование ядра SkillWharf.

## 1. Контекст и постановка проблемы

Платформа SkillWharf предназначена для запуска автономных ИИ-агентов с долговременной памятью. Агенты должны общаться с пользователями через разные каналы (мессенджеры, Web, CLI), выполнять сложные задачи, использовать внешние инструменты (Tools) и подчиняться строгим правилам безопасности и биллинга.

Нам необходимо выбрать архитектурный паттерн для компонента, управляющего сессиями, планировщиком задач, вызовом LLM и проверкой прав доступа (Paywall).

## 2. Рассмотренные альтернативы

1. **Peer-to-Peer (P2P):** Агенты общаются напрямую друг с другом и с клиентами без центрального узла.
   * *Минусы:* Критически сложно обеспечить централизованный аудит, биллинг и применение политик безопасности (sandbox). Синхронизация состояния памяти между узлами превращается в нетривиальную задачу распределенных систем.
2. **Serverless-оркестрация (FaaS):** Каждый шаг агента или вызов инструмента запускается как отдельная бессерверная функция (например, AWS Lambda).
   * *Минусы:* Высокие задержки на холодном старте (cold start). Сложность поддержания постоянных WebSocket-соединений для стриминга (SSE) и мессенджеров. Трудности с хранением долговременного состояния (памяти) между вызовами функций.
3. **Hub-and-Spoke (Центральный узел):** Единый процесс Gateway, который управляет всеми входящими и исходящими потоками, хранит сессии и маршрутизирует запросы к воркерам (Spokes).

## 3. Решение

Мы выбираем **Hub-and-Spoke**.
Центральный процесс **Gateway** берет на себя роль единой точки входа (Hub). Клиенты (Telegram, Web UI, CLI) подключаются к Gateway через WebSocket (JSON-RPC) или HTTP API. Gateway управляет сессиями, проверяет баланс (Paywall), ставит задачи в очередь и выделяет изолированную среду (Sandbox) для выполнения инструментов.

## 4. Последствия (Consequences)

**Положительные:**

* **Централизованная безопасность:** Все вызовы Tools и Skills проходят через единый слой проверки политик и биллинга.
* **Упрощение аудита:** Ledger транзакций и логи действий агентов пишутся в одном месте.
* **Единая точка подключения:** Клиентам (мессенджерам, фронтенду) не нужно знать о внутренней топологии, они общаются только с Gateway.

**Отрицательные / Риски:**

* **Single Point of Failure (SPOF):** Падение Gateway останавливает работу всех агентов.
  * *Митигация:* Проектирование Gateway как stateless-компонента (состояние выносится в PostgreSQL/Redis) для возможности горизонтального масштабирования и организации HA-кластера.
* **Узкое место (Bottleneck):** Рост нагрузки может привести к деградации.
  * *Митигация:* Асинхронная обработка задач (task plane), вынос тяжелых вычислений (Sandbox) на отдельные узлы-воркеры (Spokes).
