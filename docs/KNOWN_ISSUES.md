## Детали

### KI-001 — Образ API весил 904 МБ

**Влияние:** Долгая передача по сети, лишнее место на диске.
**План:** Использовать `corepack` вместо глобального npm, `node:24-alpine` → `distroless`, `pnpm deploy --prod`.
**Исправлено:** `pnpm deploy --prod` в builder'е и отдельная рантайм-стадия: копируются только production-`node_modules`, `dist` и `prisma` (схема + клиент). В рантайме нет npm/yarn/corepack, остаётся только Prisma CLI для `migrate deploy`. Размер — 367 МБ вместо 904 МБ, контейнер работает под непривилегированным `appuser` (UID 1001).

### KI-002 — Dockerfile не копирует packages/shared

**Влияние:** Как только в коде API появится `import { ... } from '@skillwharf/shared'`, сборка контейнера упадет.
**План:** Обновить Dockerfile, добавив копирование `packages/shared/package.json` и исходников.
**Исправлено:** Dockerfile копирует манифест и исходники `packages/shared` на обоих stage'ах.

### KI-003 — CI не собирает Docker-образ

**Влияние:** Регрессии в `Dockerfile` (забытые файлы, сломанные стадии) ловятся только при деплое.
**План:** Добавить в job `build-and-test` шаг `docker compose build api`.
**Исправлено:** Шаг `Test Docker Build` собирает образ API в CI без пуша.

### KI-004 — Нет /health и db:migrate

**Влияние:** Runbook ссылается на несуществующие эндпоинты, что вводит в заблуждение DevOps.
**План:** Реализовать в NestJS модуль HealthCheck (Terminus) и подключить ORM для миграций.
**Исправлено:** Prisma + `prisma migrate deploy` (`db:migrate`), эндпоинт `GET /api/v1/health` с проверкой БД через Terminus.

### KI-006 — Образ API вырос до 496 МБ из-за LangChain

**Влияние:** После оптимизации до 367 МБ (KI-001) образ снова вырос до 496 МБ: `@langchain/openai` и `@langchain/langgraph` тянут большой граф зависимостей в production-`node_modules`. Увеличиваются время сборки, передача по сети и занимаемое место. Локальный замер после добавления `dockerode` — 516 МБ.
**Обход:** Пока используется текущий образ; на девелоперских стендах допустимо собирать его локально.
**План:** Вынести LangGraph в отдельный воркер-сервис (Spoke), чтобы Gateway оставался лёгким, а тяжёлые LLM-зависимости жили только в воркере.

### KI-007 — Параллельные миграции при масштабировании API

**Влияние:** `prisma migrate deploy` выполняется в `entrypoint.sh` при старте
каждой реплики API. При 2+ репликах миграции запускаются одновременно; Prisma
использует advisory locks, поэтому конфликт обычно разрешается ожиданием, но
поведение зависит от версии и не гарантирует предсказуемый старт. Дополнительно
усложняются откат и диагностика: неясно, какая реплика применила миграцию и
завершилась ли она до перевода трафика.

**Обход:** Не масштабировать API на несколько реплик без внешнего механизма
миграций. Для временного масштабирования можно запускать миграции вручную
(`docker compose run --rm api prisma migrate deploy`) до старта новых реплик.

**План:** Вынести миграции из `entrypoint.sh` в отдельный init-container
(например, sidecar/Job в Kubernetes или one-shot сервис в Compose), который
завершается до запуска реплик API. Реплики API при этом стартуют без миграций.

### KI-008 — Сеть в песочнице включается глобально

**Влияние:** В MVP `SANDBOX_ALLOW_NETWORK=true` включает `bridge` всем вызовам
песочницы, а не только навыкам с разрешением `network`. Любой выполненный код
получает egress и может отправить наружу переданные секреты
(`TAVILY_API_KEY`, `GITHUB_TOKEN`). Проверка `permissions` из манифеста навыка
на уровне песочницы пока не выполняется: флаг `ALLOW_NETWORK` выставляется
доверенными инструментами Gateway, а не выводится из манифеста.

**Обход:** В production держать `SANDBOX_ALLOW_NETWORK=false` и передавать
`ALLOW_NETWORK=true` только из доверенных путей (например, `web_search` и
`exec` для навыков с `permissions: [network]`). Не запускать в песочнице
недоверенный код с секретами.

**План:** Таргетированный egress по манифесту (egress-gateway/прокси с
allowlist доменов) и проверка `permissions` при установке и вызове навыка —
следующий релиз.

### KI-009 — Интерфейс A/B-тестирования промптов не реализован

**Влияние:** В Control Plane можно создать новую версию промпта, но нельзя
запустить A/B-эксперимент, разделить трафик между версиями и сравнить
метрики. Это закрывает только часть блока 2 спецификации Control Plane
(«Версионирование и откат»), но не «A/B-тестирование на реальном трафике».

**Обход:** Переключать активную версию вручную и оценивать результат по
чату и логам; A/B-тесты проводить вне UI.

**План:** Добавить в раздел «Промпты» выбор версий, доли трафика, метрики
(latency, cost, пользовательский feedback) и остановку эксперимента. Для
этого сначала нужен API экспериментов и привязка запросов к варианту.

### KI-010 — LlmRouter использует упрощённую логику выбора

**Влияние:** Сейчас `LlmRouterService` выбирает один активный маршрут с
наименьшим `priority` для всех запросов. Нет классификации задачи, A/B-
тестирования, распределения трафика, fallback-цепочки при 429/5xx и
бюджетных предохранителей. Если выбранный провайдер недоступен, запрос
завершится ошибкой, а не переключится на резервный маршрут.

**Обход:** Держать в БД один проверенный маршрут; при проблемах провайдера
отключать маршрут (`isActive: false`) или менять его `priority` вручную.
Если активных маршрутов нет, используется env-fallback
(`LLM_MODEL`/`LLM_BASE_URL`).

**План:** Добавить правила маршрутизации по типу задачи, A/B-тесты,
fallback-цепочки и budget guardrails; покрыть выбор маршрута метриками
latency/cost. До этого считать механизм MVP-уровня.

### KI-011 — MCP-серверы Ozon и Wildberries работают в режиме заглушки

**Влияние:** Навыки `ozon-seller` и `wb-seller` объявляют инструменты
`ozon_mcp_call` и `wb_mcp_call`, но реальные MCP-серверы маркетплейсов не
подключены. Инструменты возвращают фиксированные демонстрационные данные
(например, `sales: 15000`, `items: 42`) и не выполняют реальных операций с
карточками, заказами или отзывами. Пользователь может принять такие данные
за реальные.

**Обход:** Использовать навыки только для демонстраций и тестирования
сценариев. В ответах ассистента явно помечать данные как демонстрационные;
не применять инструменты в реальных продажах.

**План:** Подключить Ozon Seller API и Wildberries API через MCP-клиент,
добавить аутентификацию по ключам продавца, таймауты, retry и маппинг
ошибок провайдера. До этого считать MCP-слой заглушкой.

### KI-012 — Навыки для внешних API работают в режиме Mock

**Влияние:** Навыки `messenger-connector`, `google-workspace`,
`midjourney-api`, `ozon-seller` и `wb-seller` возвращают фиктивные данные
вместо реальных ответов внешних сервисов. Агенты строят ответы и отчёты на
демонстрационных значениях, а пользователь может принять их за реальные.
Отправка сообщений, работа с Google Workspace, генерация изображений и
операции с маркетплейсами фактически не выполняются.

**Обход:** Использовать навыки только для демонстраций и E2E-сценариев,
явно помечать данные как демонстрационные и не подключать их к реальным
аккаунтам и продажам до появления настоящих адаптеров.

**План:** В следующем спринте подключить реальные API-ключи и адаптеры:
боты мессенджеров, OAuth для Google Workspace, Midjourney API, Ozon Seller
API и Wildberries API. Добавить таймауты, retry, маппинг ошибок провайдера
и аудит вызовов. До этого считать слой интеграций Mock.

### KI-013 — Agent Gateway покрывает только базовые regex-правила

**Влияние:** Сейчас `AgentGatewayService` проверяет только два сценария:
`execute_sandbox_code` с `rm -rf /` и `web_search` со словами
`password`/`secret`. Правила основаны на регулярных выражениях и не
учитывают обфускацию, другие опасные команды, структуру аргументов,
источник вызова, роль пользователя и контекст задачи. Модель по-прежнему
может сформировать опасный вызов, который не попадёт под эти правила.

**Обход:** Не считать Agent Gateway единственной границей безопасности:
сохранять изоляцию песочницы, allowlist секретов, paywall и HITL-одобрение
для рискованных инструментов. Подозрительные вызовы дополнительно
проверять вручную по логам.

**План:** Перейти к декларативным политикам (schema-based validation,
allowlist команд, taint tracking, роли и контекст), добавить аудит
заблокированных вызовов и покрыть правила тестами на обход. До этого
считать Agent Gateway MVP-защитой от очевидных ошибок.

### KI-014 — Content/HR/Legal навыки работают в режиме Mock

**Влияние:** Навыки `dzen-article`, `fact-checker`, `resume-screener` и
`document-analyzer` объявляют инструменты `generate_article`, `check_facts`,
`screen_resume` и `extract_document_data`, но не обращаются к реальным
сервисам. Статьи, проверка фактов, оценка резюме и извлечение данных из
договоров возвращают фиксированные демонстрационные результаты; для
`dzen-article` при этом действует Pay-per-Outcome и HITL-одобрение.

**Обход:** Использовать навыки только для демонстраций и E2E-сценариев,
явно помечать результаты как демонстрационные и не применять их для
публикации контента или кадровых/юридических решений.

**План:** Подключить реальные API и адаптеры: публикацию в Дзен, источники
фактчекинга, HR/ATS-системы и парсеры документов. Добавить проверку
качества результата, аудит вызовов и обработку ошибок провайдеров. До
этого считать навыки Mock-заглушками.

### KI-015 — Финансовые навыки работают в режиме Mock

**Влияние:** Навыки `unit-economics`, `profit-leak-detector`,
`price-monitor` и `fraud-shield-audit` возвращают фиксированные
демонстрационные значения вместо реальных расчётов и данных
маркетплейсов. `profit-leak-detector` при этом списывает Pay-per-Call, а
`fraud-shield-audit` — Pay-per-Outcome с обязательным одобрением, поэтому
пользователь может заплатить за демонстрационный результат.

**Обход:** Использовать навыки только для демонстраций и тестирования
сценариев. Не принимать на их основе решения о ценах, марже или санкциях;
помечать результаты как демонстрационные.

**План:** Подключить реальные источники данных Ozon/WB, расчёт
юнит-экономики по фактическим комиссиям и логистике, мониторинг цен и
проверку доказательного пакета. Добавить валидацию входных данных, аудит
вызовов и возвраты/отмены escrow при недостоверном результате. До этого
считать финансовые навыки Mock-заглушками.
